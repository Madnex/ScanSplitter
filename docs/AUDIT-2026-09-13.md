# ScanSplitter codebase and product audit

Date: 13 September 2026. Scope: current working tree, including the review-workflow changes already in progress when the audit began. Small fixes were applied during the audit. The owner subsequently approved all six larger packages; implementation is recorded in the [hardening contract](specs/audit-hardening-2026-09.md). The findings below preserve the original audit evidence.

## Assessment

ScanSplitter has a useful working core and sensible foundations: local processing, reversible crop geometry, atomic project manifests, explicit cloud disclosure, shared filename sanitization, structured background-job errors, and a passing CI-style test suite. The existing monochrome interface keeps attention on photographs and has reasonably consistent spacing, borders, and controls.

It is not yet as dependable or intuitive as its family-archivist positioning suggests. The largest issue is archival integrity: imported originals are not actually retained unchanged. Next come interrupted-job recovery, navigation after failed saves, and differences between export paths. Visually, the app is coherent but utilitarian and crowded. Better hierarchy, workflow consistency, and trustworthy status language matter more than a font or color overhaul.

## Larger findings

P1 means possible loss of work, source fidelity, or misleading archival output. P2 means reliability, usability, or maintainability debt that materially affects repeated use.

### 1. P1 — Projects discard source fidelity during import

**Evidence:** `src/scansplitter/projects.py:486` converts uploads to RGB and saves every non-PNG image as quality-95 JPEG. `_store_pdf` at line 503 renders at **150 DPI**, saves JPEG pages, and deletes the incoming PDF. PNGs are also decoded and re-encoded. A TIFF probe produced a `.jpg` with different bytes; there is no retained original to recover from.

**Impact:** TIFF/16-bit/color-profile/metadata fidelity can be lost immediately; PDF exports are limited by the stored 150-DPI render. “Lossless master” output cannot restore information already discarded on ingest. “Originals stay untouched” is misleading for the project's retained copy, even though the user's external file is not modified.

**Proposed change:** Retain immutable source bytes and a checksum, create separate display/detection proxies, crop from the source, and version the storage schema. Existing projects need an explicit migration/relink strategy: previously discarded originals cannot be reconstructed.

### 2. P1 — Quick PNG exports and rotations already pass through JPEG

**Evidence:** `api.py:406` / `api.py:862` return quality-85 JPEG crop data. `frontend/src/App.tsx:639` re-encodes each rotation as JPEG. `ResultsGallery.tsx:94` converts this JPEG to PNG when requested.

**Impact:** “PNG (lossless)” describes the final container, not lossless extraction from the scan. Repeated rotations add JPEG generations.

**Proposed change:** Store original crop references plus rotation metadata; render once from the source into the requested format. Keep previews explicitly separate from downloadable assets.

### 3. P1 — Interrupted detection can remain stuck, and stale work can win

**Evidence:** `projects.py:688` persists `detecting` before submitting to an in-memory executor (`jobs.py:109`). There is no startup reconciliation. A fresh `ProjectStore` after a simulated interrupted queue still returned `detecting`. Cancellation at the first progress callback in `_detect_and_persist` also left that status unchanged. Completion persists new boxes without a per-scan generation/revision check.

**Impact:** A restarted or cancelled scan can appear busy indefinitely; overlapping detection or editing can allow an old result to replace newer work. Project deletion does not coordinate its files with outstanding jobs.

**Proposed change:** Add scan/job revisions, per-scan scheduling, explicit cancellation state transitions, startup recovery, and coordinated deletion. Do not silently re-send interrupted cloud scans or incur repeat charges on restart.

### 4. P1 — Review navigation can leave after a failed save

**Evidence:** `ReviewMode.tsx:140` returns `false` when persistence fails. `goTo` at line 183 ignores that return value and changes scans; `handleBack` at line 324 runs navigation in `finally`. Other dependent actions also ignore the boolean.

**Impact:** A network or filesystem failure can be followed by navigation that discards the user's editing context. Controls and hotkeys also need protection against overlapping save/approve actions.

**Proposed change:** Centralize save-before-navigation, block dependent actions on failure, keep the draft visible, and serialize writes with stale-response guards. Include mode switching and browser navigation in the same draft-preservation policy.

### 5. P1 — Quick PDF edits are only stored for the currently selected page

**Evidence:** `UploadedFile` has one `boxes` array. `App.tsx:448` and `App.tsx:946` clear it on page changes. Crop sources and batch work use mutable file-array indexes.

**Impact:** Revisiting a PDF page discards its manual box adjustments and triggers detection again; “Crop All” cannot represent every edited PDF page. Closing files while work is running makes index-based attribution harder to keep correct.

**Proposed change:** Key scan state and results by immutable session/file/page IDs, retain per-page drafts, and define batch scope in scans/pages rather than uploaded-file objects.

### 6. P1 — Preview downloads do not share the archival export contract

**Evidence:** `ResultsGallery.tsx:94` downloads raw crop data without writing the edited date or GPS policy. Project crop/lightbox routes also serve JPEG previews, whereas project ZIP export applies archival metadata and restoration. The lightbox format inconsistency was fixed, but the common download path still needs work.

**Impact:** Users can receive different metadata, processing, resolution, and format behavior depending on which Download/Export button they choose.

**Proposed change:** One canonical rendering/export service for individual files, ZIPs, local folders, and delivery; consistent format/metadata options and a clear distinction between preview download and archival export.

### 7. P1 — “OK” is stronger than the current confidence evidence

**Evidence:** In the mixed-print fixture, a detected box visibly omitted the upper portion of a photo, yet Projects showed `OK · 6` and “No issues flagged.” `confidence.py:75` checks geometry heuristics; absence of those flags becomes `auto_approved` in `projects.py:726`. The existing v5 benchmark reports 100% count accuracy but only 74.1% strict F1 at IoU 0.85 across ten cases.

**Impact:** Finding the correct number of rectangles does not establish correct boundaries or orientation. The app may encourage users to export damaged crops without review.

**Proposed change:** Evaluate automatic approval against actual crop correctness, add challenging real-scan fixtures with consent, and distinguish “no issues detected” from “reviewed by you.” Calibrate thresholds before expanding automatic approval.

### 8. P2 — Large collections have several unbounded memory paths

**Evidence:** `api.py:1406` accumulates every uploaded file's bytes before ingestion, with only per-file limits. PDF rendering calls `get_pixmap` before an output-pixel budget is checked (`pdf_handler.py:46`). Each project crop preview decodes the full scan and runs processing independently (`projects.py:648`). ZIP artifacts remain as bytes in the job registry; cleanup is driven by registry activity. Quick keeps base64 image data in React and sends it back for export.

**Impact:** A modest number of high-resolution scans or simultaneous previews can use very large amounts of RAM; a compressed-file cap does not bound decoded image memory.

**Proposed change:** Stream/stage uploads, enforce aggregate and decoded-pixel limits, bound the job queue, cache revisioned previews, and serve disk-backed export artifacts with scheduled cleanup. Measure peak memory on a representative collection before selecting limits.

### 9. P2 — Import failure is not transactional

**Evidence:** `projects.py:453` writes image files before updating the manifest. A valid image followed by a corrupt image left one unreferenced file in an isolated probe. Partial PDF failures have the same pattern. Quick's upload loop stops at the first failure after earlier files may already have succeeded.

**Proposed change:** Stage each batch, either commit it atomically or report per-file successes/failures, and clean abandoned artifacts. Give the UI a useful retry result without re-uploading successful files.

### 10. P2 — Project polling can stop after one failed fetch

**Evidence:** `useProject.ts:19` catches errors without changing `project`; its one-shot poll is scheduled by an effect dependent on `project` at line 50. A failed poll therefore does not schedule another one. Responses are not guarded against newer requests or target changes.

**Proposed change:** A cancellable polling loop with bounded retry/backoff, an explicit connection state, request ordering, and reconciliation with optimistic edits. Test transient failures and out-of-order completion.

### 11. P2 — Quick/Projects feature parity and language have drifted

**Evidence:** Quick uses Photos/Album pages and Local/Cloud AI choices plus advanced area settings and auto-rotation controls. Project overview instead exposes raw detector versions; its UI has no matching area or auto-rotation controls, although the settings exist in the backend. The binding project spec requires parity unless an exception is recorded.

**Impact:** Switching modes changes both terminology and available controls. Users must understand implementation versions to perform the same task.

**Proposed change:** Share a settings model and common controls, keep an obvious recommended default, and place version selection in advanced settings. Add regression coverage for both workflows whenever a shared option changes.

### 12. P2 — The interface needs a clearer sequence and better responsive editing

**Observed:** Quick initially presents settings before the user has any scan, spreads upload/crop/export across three panels, and places actions below scrolling settings. Projects exposes many equally weighted actions; export settings are partly hidden under “Process.” The initial distinction between temporary Quick work and persistent Projects is not explained in visible onboarding copy. Review shows numerous per-photo fields simultaneously.

**Remaining:** The small layout fixes remove the immediate Quick overlap and desktop toolbar clipping. A full narrow-screen review layout, canvas resize handling, zoom/pan, visible save state, and touch-friendly editing still need dedicated work. `ImageCanvas` fits the image on URL load and has no container resize observer. A bitmap disappeared during hot reload while boxes remained; treat that as a development-lifecycle observation requiring a focused reproduction, not a proven production failure.

**Proposed change:** Keep the current visual direction, but make Upload → Review → Export the primary path. Use an inspector for the selected photo, put delivery choices in one export surface, and give small screens separate settings/editor/results views. Choose whether mobile supports full editing or primarily review/export.

### 13. P2 — Accessibility remains incomplete outside the repaired controls

**Evidence:** Metadata, pairing, comparison, and lightbox overlays are still custom modal-like elements without complete focus management. Review hotkeys exclude inputs/textareas but not selects or focused buttons, so arrow/Enter handling can conflict with native controls. Sliders and several output fields lack explicit accessible labels. The canvas is primarily pointer-driven. There is no main landmark/skip link.

**Proposed change:** Extend the modal pattern, scope shortcuts to the active surface, label remaining fields, and provide an accessible box list with numeric geometry editing. Validate keyboard-only navigation and an actual screen reader; automate browser accessibility checks.

### 14. P2 — Metadata and pairing contain unfinished or misleading affordances

**Evidence:** The metadata form offers OpenStreetMap lookup, but `api.py:1505` always returns 503 because lookup is disabled. The form describes metadata as JPEG-only while the encoder also writes PNG/TIFF metadata. Changing metadata scope resets unsaved edits without notice. The front/back UI does not show existing relationships or offer unlinking; `pair_scans` prevents self-pairing but does not enforce an acyclic front/back model.

**Proposed change:** Hide/disable unavailable capabilities using server capability data, explain metadata interoperability precisely, protect dirty forms, and provide visible current pairing plus unlink/reassign actions. Decide the pairing invariants before changing storage.

### 15. P2 — Request validation is inconsistent and too permissive

**Evidence:** Project settings are a dictionary, and only some enum fields are validated (`projects.py:352`). A probe accepted `min_area_ratio="invalid"`, `auto_rotate="false"`, and `quality=-3`. Box models do not consistently enforce finite coordinates, positive dimensions, unique IDs, or image-relative limits. Project export name allocation is case-sensitive, unlike common target filesystems.

**Proposed change:** Typed shared request/settings models; reject invalid values at the API boundary; validate cross-field constraints; define portable filename collision behavior. Keep explicit-null metadata semantics intact.

### 16. P2 — Delivery needs a stronger retry and credential contract

**Evidence:** Delivery builds a whole ZIP before dispatch and does not check cancellation during individual remote uploads. There is no persisted per-file progress or resume record. Password strings are stripped by the form, API, and vault normalization, which can alter valid credentials. Saved connection data can be combined with an explicitly changed server URL.

**Proposed change:** Preserve passwords exactly, bind saved secrets to an explicit connection identity, define overwrite/idempotency behavior, and record per-file results for safe retries. Test against disposable target instances before changing live delivery. This audit made no external delivery requests.

## Streamlining and implementation packages for approval

| ID | Proposed package | Scope / acceptance criteria |
|---|---|---|
| A | **Preserve originals and unify archival rendering** | Large, storage migration. Covers findings 1, 2, and 6. Original bytes/checksums retained; previews separate; rotations non-destructive; individual/ZIP/folder exports agree on pixels and metadata. |
| B | **Reliable jobs, saves, and per-page state** | Large behavior change. Covers 3–5 and 10. Failed saves retain drafts; interrupted jobs recover without automatic cloud charges; stale results cannot overwrite new edits; PDF pages retain boxes. |
| C | **Simplify and unify the UI** | Medium/large product change. Covers 11–14. Shared settings, explicit workflow and export surface, usable responsive review, scoped keyboard controls, completed metadata/pairing affordances. Keep the existing stack and restrained visual style. |
| D | **Bound resource use and make imports/delivery recoverable** | Large infrastructure change. Covers 8, 9, and 16. Bounded memory/queue/pixel budgets, staged imports, cached previews, disk-backed exports, resumable delivery and tested credential handling. |
| E | **Calibrate detection and approval confidence** | Medium research/validation change. Covers 7. Measured false-approval rate on representative scans; status wording matches what is actually known; preserve manual review. |
| F | **Extract shared services and strengthen regression tests** | Medium, incremental refactoring. Covers 15 and the structural debt below. Typed requests, shared detector/render/export services, lifecycle integration tests, browser workflow tests; preserve API behavior except approved validation tightening. |

Recommended order: **A and B first**, with F supporting those changes; then C, D, and E according to whether usability, collection size, or automatic approval is the next priority. Do not combine all six into one rewrite.

Structural debt: `api.py` is approximately 1,660 lines, `projects.py` 1,266, `App.tsx` over 1,100, and `detector.py` 1,449. More consequential than file length is repeated detector dispatch, image encoding, error handling, and divergent export contracts. Extract domain services before mechanically splitting routers. Frontend tests mostly exercise pure helpers and server-rendered markup; they miss focus, async saves, canvas lifecycle, and navigation races. Add a small set of behavior-driven browser/integration tests. The production JS entry is about 639 kB minified / 193 kB gzip and triggers the build warning; lazy-load the benchmark screen and heavy editing surfaces after measuring startup cost. CI builds the frontend again for packaging; passing the tested build as an artifact would remove duplicate work. Update stale roadmap/spec statements alongside the approved behavior changes.

Packages A–F have been implemented in the working tree. See the binding addendum for exact behavior and explicit migration/validation limits. New regression coverage verifies originals and PDF resolution, failed imports, interrupted and stale jobs, save conflicts, canonical downloads, delivery resume, page drafts and async UI behavior. Real-scan confidence calibration, production-volume memory/delivery certification, and physical screen-reader validation are not claimed. No user project was modified during validation, and no external delivery or publication was performed.

### Final implementation validation

- **176 backend tests and 31 frontend tests passed.** Ruff, frontend lint, TypeScript checking, the production build, and `git diff --check` passed. The dependency audit reported zero npm vulnerabilities after compatible updates. Remaining backend warnings come from Starlette/httpx and PyMuPDF dependencies.
- Live browser checks used an isolated temporary project store: upload and detection, numeric crop editing, dirty-draft navigation protection, saved-edit persistence, review approval, and a completed PNG ZIP download with additional TIFF masters. Quick upload/detection/cropping, zoom/Fit, native lightbox dismissal and focus restoration, and desktop/narrow (390 px) layouts were also inspected.
- The production entry is approximately **193 kB minified / 61 kB gzip**; the editing application and benchmark are loaded separately. The previous oversized-chunk build warning is resolved.
- The repeatable export baseline used 20 synthetic repository scans and produced 67 photos in 4.46 seconds, with **162.2 MiB peak process memory**. The largest source was 1.4 MP and no ML restoration was enabled. This is not a capacity guarantee for large archival scans or model inference; see `benchmarks/results/export-profile.json`.
- Original-byte tests include ICC-tagged images and 16-bit TIFF. Source bytes are retained, while processed derivatives are 8-bit RGB; embedded raster color profiles are converted to sRGB for processing.

The implementation preserves and incorporates the review/lightbox edits that were present before this audit. A subsequent readability pass widened the Quick settings sidebar, enlarged shared controls, removed nested padding, and moved the three-column layout to wider screens. Its desktop and narrow-screen checks, 31 frontend tests, lint, and production build passed.
